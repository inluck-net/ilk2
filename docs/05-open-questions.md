# 5. Open questions

Each question is decided at the phase its Status names (most before or during P1). Each has a proposed default; Chad decides. Record decisions in the Status column. The defaults below were revised on Oct 13 after the Codex review.

| # | Question | Proposed default | Why it matters | Status |
|---|---|---|---|---|
| Q1 | Dispatch layer: Claude Agent SDK or the Claude Code CLI? | A dispatch-adapter interface, with the CLI as the baseline known to work with MiMo. Adopt the SDK only if P1 proves, with MiMo: compatibility, stable session identity on resume, hook parity, cancellation by process group, streaming timing metrics and the same sandbox behaviour ([document 2](02-architecture.md) §2.6) | Decides how sessions, resume and hooks are controlled, and whether stream-log parsing can go | **CLI, Oct 13** (P1 step 2: the SDK passes all 6 criteria only behind the same wrapper; judgment call; docs/spikes/p1.md) |
| Q2 | Plan format: keep V1 Markdown, or define an ilk2 JSON/YAML format? | Import V1 Markdown unchanged; define a JSON form for machine submitters (gh-resolve) | Keeps `/ilk-plan` working without changes | open |
| Q3 | Where do plans live once submitted? | An immutable normalized plan snapshot in SQLite is canonical, and the original imported documents are stored beside it. Rendered Markdown is an atomic, version-labelled projection for humans. Amendments are version-checked, limited to steps that have not started, and recorded in an append-only journal | V1's plan files with several writers are root cause 2; rollback needs the export in [document 4](04-v1-relation-and-migration.md) §4.3 | open |
| Q4 | Consumer interface: CLI with JSON, or a local socket? | CLI with JSON and `api_version` | gh-resolve already shells out; a socket adds lifecycle burden | open |
| Q5 | First real consumer for P3? | Choose by criteria: deterministic local gates, no production writes or credentials, representative multi-step work, suite under 5 min, easy rollback. Provisional: `todo-triage`, if it meets them; `gh-triage` otherwise | Low risk, but must have real gates | open |
| Q6 | Retry policy per step (attempts, resume vs fresh session)? | 3 attempts; resume the same session with red evidence; a fresh session on the 3rd | Needs data from P2 | judgment call |
| Q7 | Attempt time cap? | 60 min (V1's current), measured and revisited after M1 | V1 timeouts were often caused by gates that could not pass, not by slow work | judgment call |
| Q8 | Does ilk2 run its own CI full suite? | Yes, on every push (macOS runner) while the suite stays under about 5 min | Keeps V1's no-full-suite workarounds out of V2 | open |
| Q9 | ilk-skills repo visibility vs ilk2 | ilk2 private; ilk-skills is public today | Decide whether ilk2 should match | **public, Oct 13 (Chad)**: the free GitHub plan's private-repo Actions minutes ran out (macOS bills at 10x). History audited first, all 57 commits: 0 credentials, 0 customer or tenant names; references to private kira-cloudflare and gh-resolve, of the kind public ilk-skills already carries. CI back: 178 passed on `6ac543b` |
| Q10 | What does the brief preload, and which worker settings are set per project? | P1 runs a counterbalanced comparison: several representative V1 steps, each run with a discovery brief and a preloaded brief, in fresh worktrees and sessions, alternating which goes first. Adopt preloading only if total minutes per accepted step fall without lower acceptance or more repair attempts. Record effort, thinking settings and the model per attempt; the Oct 14 flash trial is the first model input | The time before the first edit (42%) overlaps with thinking (56%) and is not all discovery ([evidence](evidence/2026-10-12-v1-stuck-and-slow.md) §2); one step run twice is open to order and caching effects | **adopted Oct 13** (P1 step 4: 26.99 → 20.59 min per accepted step, faster on 4 of 4 steps in both orders, acceptance 4/4 both, attempts 5 → 4; judgment call under Chad's standing authorization, re-measured in P3; docs/spikes/p1.md) |
| Q11 | Progress bounds | The values in [document 2](02-architecture.md) §2.11.5, each a judgment call with what would prove it wrong. They now include supervisor health, spawn, outer run bound, kill escalation, SQLite busy, drain, a 24 h ceiling on quota waits, and re-notification | They decide how fast a stall is caught and when a human is called. Too tight causes false stalls; too loose is V1's silent waiting | judgment call |
| Q12 | How is a human told? | A durable `needs_human` row acknowledged with `ilk2 ack`. Per-project policy ([document 2](02-architecture.md) §2.11.3): `owner` projects get macOS plus **one off-host channel**, re-sent after 4 h then every 12 h; `consumer` projects (resolver) get the event only, with one off-host notice after 24 h unacknowledged. Proposed off-host channel: a Lark bot message if the existing Lark app can send messages, otherwise Teams | A local notification does not prove delivery; ADR 0032 (gh-resolve, amended Sep 17) leaves the merge as the only human gate for resolver runs | **decided Oct 13 (Chad): notifications are opt-in.** A project pages only if it configures a channel (Lark is one option, never a default). The default is the durable row plus an event. Pages are the last rung, not the first response: see [document 6](06-open-items.md) "Self-resolution" |
| Q13 | Supervisor restart: adopt surviving drivers, or kill and requeue? | Kill and requeue for M1 (I4); add a driver lease and handshake only if restarts exceed one a day | Adoption without a lease breaks I4; kill-and-requeue costs the attempt in flight | accepted Oct 13 ("go ahead") |
| Q14 | A new failure from an earlier step: who repairs it? | Up to M1: the current step, with the failure marked `possibly-inherited`. Before P4: attribution by walking backwards through accepted commits in diagnostic worktrees to the most recent clean-to-failing edge, confirmed by re-probes, with a budget. An attributed failure gets a deduplicated batch-level repair plan that blocks the rest of the batch; flaky, changed-gate or out-of-budget cases are `unattributable` ([document 2](02-architecture.md) §2.5.4, §2.5.7) | gh-resolve review H2: two 60-minute iterations repaired another step's damage. Codex review 2: the first design had no valid repair transition and no reproducible probe environment | accepted Oct 13; deferred to before P4 (Chad) |
| Q15 | ilk2 runs per host while V1 shares it | ilk2 starts at 2, as an experiment guarded by host-load admission; budgets limit starts, not resources ([document 4](04-v1-relation-and-migration.md) §4.2) | A limit of 1 makes P5 serial (gh-resolve review H1); two independent budgets cannot prevent starvation on a shared CPU and quota (Codex review 2) | accepted Oct 13 (judgment call) |
| Q16 | Full suites inside the worker | Blocked by a hook; the brief asks for targeted tests only ([document 2](02-architecture.md) §2.6) | About 13 min per iteration on rezmac went to the worker's own suite plus the driver's gate (gh-resolve review M1) | accepted Oct 13 |
| Q17 | Plan the whole batch up front, or plan steps as it runs? | Fixed step lists for M1, as designed. P1-P2 keep an evidence table with denominators. At M1, decide whether a planning pass may propose amendments to pending steps, applied only by the driver, inside a sealed goal and set of verification obligations, with monotonic step and planning budgets ([document 6](06-open-items.md) P2-1) | Later steps are written against assumptions earlier steps test; P1 step 1 already found a hazard the plan did not name | open; decided at M1 (Chad, Oct 13) |
