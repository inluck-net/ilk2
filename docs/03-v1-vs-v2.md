# 3. V1 vs V2

V2 changes how the engine is built, not what it is for. The same plans, worker model, consumers and two hosts stay. What changes is who owns state, how identity and liveness work, how gates decide, and how code is deployed.

## 3.1 Side by side

| Area | V1 (ilk-skills at `d17ffdcd`) | V2 (ilk2) |
|---|---|---|
| Engine code | About 110.7k non-test lines across Python, Bash and PowerShell; runner 8,695 lines of Bash plus a 2,929-line PowerShell twin | Core target about 4.7k lines of Python 3.12; no shell orchestration |
| Who changes batch state | Worker edits frontmatter and bumps steps; the driver does so only on some paths; code-only mode is opt-in | Driver only (I1); the worker has no write path |
| State storage | Markdown frontmatter, JSON and JSONL files, shell globals; several writers | One SQLite store; versioned transitions with a journal (I2) |
| Identity | Project key derived from the path; worktree-vs-clone switch per host | Declared at submission; never derived (I3) |
| Liveness | pgrep, argv, PID files, wrapper PIDs; registry on most paths after Oct 12 | Supervisor owns its children; PID plus start time in the store (I4) |
| Shipping | Worker or driver ship scripts, `gate_first` markers, ship-integrity checks, release-train audits | The driver's accept of a plan's last step ships it, in the same transaction |
| Gate outcomes | Pass or fail; harness errors and missing tests often read as red; base reds handled per case | `pass` / `fail` / `unmeasured`; base reds measured once and excluded (I5, I6) |
| Added checks | Mention gate guesses the runner (bare `vitest run`) | Only an adapter that resolves the owning config can add a check |
| Deploy | Release layout now, but with a long live-clone history; self-modifying batches | Immutable releases with bundled Python; drain at step boundary (I7) |
| Concurrency on one project | One runner per derived key (rezmac resolver runs one at a time) | Limit set per project; parallel batches by declared roots |
| Consumer contract | gh-resolve reads ilk's files and layouts directly | Versioned CLI JSON (`api_version`) |
| Platforms | Mac plus partial Windows | Mac only (I8) |
| Terminal reasons | "timeout" used for no-dispatch iterations; deadlocks loop silently | Every terminal state named (I9) |
| Refusing queued work | Release train, batch audit, permits, blacklist and no-progress bound: about 0.8 h refused per hour worked (Sep 15 to Oct 12) | No guards that re-check driver-written state; every refusal names its clearing action and actor, and refused hours are reported (I10) |
| Keeping a batch moving | Watchdog and scheduler guess from PID files and logs; relaunch storms, escalation loops, a blocked dependency re-dispatched all night; no notification | Every non-terminal state has a time bound and an action when it passes (I11, [document 2](02-architecture.md) §2.11); checks at submission; one notification when a human must act; a 12-case stall suite gates M1 |
| What the worker must discover | Brief names the step; the worker explores the repo. 42% of wall time passes before the first edit | The driver preloads named files, symbols, tests and red output; minutes to first edit is measured (§3.4) |

## 3.2 Advantages

| Advantage | Why it follows | How we will know |
|---|---|---|
| **Truthful state by construction** | The worker cannot write state; the driver writes only through versioned transactions | Zero state changes by any actor other than driver, supervisor or human, checked from the journal |
| **Less time stuck** | Shipping is a driver transition, so there is nothing for a train, audit or permit to guard. Those three were 69-74% of V1's refused hours. Any remaining refusal names who clears it (I10) | Refused hours per hour worked, compared with V1's ≈0.8 |
| **Fewer wasted attempts** | No no-dispatch iterations, no gate that can never pass, no shipping deadlocks; unmeasured gates surface immediately | Share of attempts that produce nothing, compared with V1 (today 1/5 to 3/8) |
| **Never silently stuck** | Each wait has a bound, each retry has a limit, and each human state notifies once (I11) | Stall suite S1-S12 passes at M1; in production, 0 runs exceed a bound without a recorded action |
| **Recoverable** | Crash recovery is a reconcile over the store, and runs restart from the last accepted commit | Kill the supervisor and the drivers mid-batch in a test; the batch still ships |
| **Parallel by design** | Declared roots plus per-project limits | Two gh-resolve issues running at once on one host |
| **Small and reviewable** | About 4.7k lines in one language | Line budget enforced in CI |
| **Safe upgrades** | Immutable releases; drain at step boundaries | Upgrade during a live batch with zero lost or duplicated steps |

## 3.3 What V2 will not fix (non-goals)

- **The model's raw speed.** V2 does not make MiMo think faster per token. What drives the worker's time is in scope, though: see §3.4. (Until Oct 12 this whole item was a non-goal. The evidence moved it.)
- **Slow consumer test suites.** A gate takes as long as the consumer's tests. V2 avoids running gates that cannot pass, but it does not speed tests up.
- **Plan quality.** A badly scoped plan fails in either version. Planning stays with V1's `/ilk-plan` and `ilk-spec` for now.
- **Windows.** Out of scope.

## 3.4 Worker time is in scope

On Oct 12 (24 iterations, 998 min), model thinking ran for 56% of iteration wall time, and 42% passed before the first edit. Worker-run tests took 7%; the driver's audit took 1.9% ([evidence](evidence/2026-10-12-v1-stuck-and-slow.md) §2). Removing orchestration waste alone leaves most of a step's time untouched. The engine controls four inputs to worker time:

| Lever | What V2 does | How it is measured |
|---|---|---|
| **Brief contents** | The driver preloads the files, symbols, tests and red output the step names, so the worker starts editing instead of exploring ([document 2](02-architecture.md) §2.6) | Minutes to first edit, with a preloaded brief and with a discovery brief, on the same step (P1) |
| **Step size** | Import warns on steps whose scope spans many files or modules; plan authors split them | Minutes per accepted step by step scope |
| **Effort and thinking settings** | Recorded per attempt; set per project, not hidden in a worker home | Thinking share and acceptance rate per setting |
| **Model** | The worker model is a per-project setting; the Oct 14 flash trial is the first input | Minutes per accepted step and acceptance rate per model |

## 3.5 Expected effect on speed (prediction, not a claim)

V1 today: 84-93 min per accepted step, all attempts counted.

V2 removes three kinds of lost time:
- **Refused hours:** queued work waiting behind the train, audit and permit guards. This is wall time between steps, not time within a step.
- **Wasted attempts:** iterations that dispatched nothing, timeouts on gates that cannot pass, re-dispatching finished work, and deadlocks.
- **Discovery time:** what preloading saves before the first edit (§3.4).

The first two follow from the design. The third is a hypothesis the P1 spike tests. Until then, the fair expectation is that V2 is faster per accepted step roughly in proportion to V1's wasted-attempt share, and finishes batches sooner by most of the refused hours. Each of these must be measured, using [document 4](04-v1-relation-and-migration.md)'s acceptance criteria, before anyone claims it.
